# Стабілізація перевернутого маятника на візку (Cart-Pole)

Стенд: ESP32 + кроковий NEMA 17 (KS 42BYGHW811) через TB6560, пасова передача,
енкодер маятника LPD3806 (2400 тіків/оберт), два кінцевики. Зараз — одинарний
маятник; подвійний — наступний етап (`hybrid_mpc_lqr/`, `mpc_sim/`).

## Головна ідея: один код керування для заліза і симуляції

```
common/controller.c   ← ядро керування (стани, оцінювач, LQR, підйом, SysID)
        │
        ├── esp32_cart_pole/      прошивка: викликає ctrl_step() на 500 Гц
        └── single_pendulum/      симуляція: той самий controller.c через ctypes
                                  + модель стенду common/host/plant_sim.c
```

Симулятор поводиться як стенд не тому, що «схоже налаштований», а тому, що
виконує **ту саму прошивку**. Різниця з реальністю зводиться лише до
параметрів моделі маятника — їх вимірює `sys_id.py`.

Параметри — в одному місці:

| Файл | Що | Хто змінює |
|---|---|---|
| `common/cart_pole_config.h` | піни, геометрія, межі, пороги | вручну |
| `common/pendulum_params.json` | ω0, тертя, запізнення приводу, ваги LQR | `sys_id.py` / вручну |
| `common/pendulum_params.h` | ті самі параметри + коефіцієнти LQR для C | **генерується** `single_pendulum/params.py` |
| `common/swingup_trajectory.h` | траєкторія підйому + TVLQR | **генерується** `single_pendulum/mpc_generator.py` |

## Швидкий старт

```bash
python -m venv venv && ./venv/bin/python -m pip install -r requirements.txt

# Симулятор (Pygame) — цифровий двійник стенду
./venv/bin/python sim_pygame.py

# Автоперевірка прошивки в симуляції (9 варіантів розбіжності моделі)
./venv/bin/python single_pendulum/selftest.py

# Прошивка
. ~/.espressif/v6.1/esp-idf/export.sh
idf.py -C esp32_cart_pole -p /dev/ttyUSB0 build flash

# Панель керування стендом
./venv/bin/python cli_control.py --port /dev/ttyUSB0
```

Без заліза: `./venv/bin/python single_pendulum/virtual_stand.py` створює
віртуальний порт `/dev/pts/N`, з яким `cli_control.py` і `sys_id.py`
працюють так само, як зі стендом.

## Робочий цикл зі стендом

1. **Увімкнення.** Маятник має *висіти спокійно* (це початковий нуль; далі
   нуль сам коригується, коли маятник у спокої). Візок їде до лівого стопера
   (калібрування X), виїжджає в центр, гасить коливання, переходить в
   `ОЧІКУЄ 's'`.
2. **SysID** (раз після будь-якої зміни механіки):
   `./venv/bin/python sys_id.py --port /dev/ttyUSB0 --flash`
   — стенд сам проганяє 3 тріали, скрипт підбирає параметри, перевіряє їх на
   тріалі, що не брав участі у фіті, перераховує LQR і траєкторію, проганяє
   автотест і прошиває.
3. **Підйом:** `S` у `cli_control.py`. Стоп: `X` або пробіл.

Команди по UART: `s` підйом · `x`/пробіл стоп · `h` хомінг · `c` поточне
місце = центр · `i` SysID.

## Як працює керування

| Режим | Закон | Навіщо так |
|---|---|---|
| Позиція візка | лічильник **реально виданих** кроків (PCNT на піні STEP) | не «з'їжджає» від інтегрування команди |
| Будь-який рух | обмеження прискорення + швидкість обмежена гальмівним шляхом до меж рейки | без миттєвих зупинок → без пропуску кроків |
| Гасіння внизу | `a = K·ω·cosφ` + м'яке центрування | завжди забирає енергію (старе `v = −k·ω` майже не гасило) |
| Баланс | дискретний LQR з інтегратором X на кінематичній моделі | коефіцієнти з моделі, а не вручну |
| Підйом | оптимальна траєкторія (CasADi) + **TVLQR** зворотний зв'язок | старий варіант програвався наосліп |
| Кут/ω | оцінювач з моделлю маятника | альфа-бета без моделі запізнювався на ~25 мс |
| Нуль енкодера | ставиться при старті, коригується, коли маятник нерухомий 1 с | «низ = 60°» виправляється сам |

## Що виправлено зі списку проблем

| Проблема | Причина в старому коді | Тепер |
|---|---|---|
| Погано працює занулення | `v = −k·ω` зсуває частоту, але майже не забирає енергію | енергетичне гасіння `a = K·ω·cosφ` |
| MPC занадто швидко розганяє | траєкторія до 8.5 м/с², ривок ~360 м/с³, 0.7 м/с; без обмежень у прошивці | ≤3.5 м/с², ривок ≤50 м/с³, ≤0.5 м/с, замкнений контур |
| Після маневру низ = 60° | `encoder_reset()` при SysID-таймауті / хомінгу, коли маятник ще хитався; переповнення PCNT губилося | нуль лише в спокої + автокорекція; watch point для PCNT |
| З'їжджає центр рейки | X = інтеграл команди + `cart_x = 0` у кількох місцях + миттєві зупинки | X з лічильника кроків, переписується лише стопером/хомінгом |
| Не їде вліво | найімовірніше: сирий (без дебаунсу) лівий стопер обнуляв рух вліво й «телепортував» X; плюс X, що з'їхав, упирав візок у програмну межу | для логіки — тільки стан після дебаунсу, X з лічильника кроків. Якщо лишиться — дивіться `L:` у телеметрії та «Апаратні рекомендації» (DIR від 3.3 В) |
| Вал крутиться, візок ні | люфт паса/шківа + дрібні реверси балансу від квантування енкодера (у симуляції ≈5 мм розмаху, ~15 реверсів/с) | механіка (натяг, лиска); у симуляції є модель люфту — баланс тримається до 2 мм |

## Апаратні рекомендації

- **TB6560 і частота кроків.** За даташитом ≈15 кГц максимум; при 50.6 кроків/мм
  це 0.3 м/с, а підйому потрібно до 0.5 м/с (25 кГц). Якщо `sys_id.py` дає
  κ < 0.95 або при контакті зі стопером друкується велика корекція X — зменшіть
  мікрокрок удвічі й перекалібруйте `STEPS_PER_METER` (`esp32_step_calibration`).
- **Енкодер:** зовнішні підтяжки 2.2–4.7 кОм до 3.3 В на A/B; кабель енкодера
  окремо від дротів мотора.
- **DIR/CLK від 3.3 В** на оптопари TB6560 (розраховані на 5 В) — на межі; якщо
  напрямок інколи «не перемикається», поставте буфер на 5 В (напр. 74HCT245).
- **Люфт:** натяг паса, гвинт шківа — на лиску вала.

## Структура

```
common/                    спільний C-код і параметри (див. вище)
  host/                    тільки для ПК: C API для Python і модель стенду
esp32_cart_pole/           основна прошивка (main.c — обгортка над ядром)
esp32_hardware_test/       тест вузлів стенду
esp32_step_calibration/    вимірювання STEPS_PER_METER
single_pendulum/           симулятор, генератор траєкторії, автотест, віртуальний стенд
sys_id.py                  ідентифікація параметрів зі стенду
cli_control.py             панель керування стендом
hybrid_mpc_lqr/, mpc_sim/  подвійний маятник (поки модель з умовними параметрами)
```
